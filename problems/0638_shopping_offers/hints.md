# 638. Shopping Offers

## 核心思路

这是一个**多维背包 + 记忆化搜索**问题。对于每种"需求状态"（还需要买多少件各类物品），我们尝试使用每个大礼包，如果使用后不超出需求就递归求解子问题，最终取所有方案中的最小花费。用 `map` 记忆化避免重复计算。

## 思维链

1. **分析状态**：当前还需要购买的物品数量组合 `needs` 就是状态
2. **决策空间**：对于当前状态，可以选择：
   - 不用任何大礼包，按原价逐个购买 -> 基线花费
   - 尝试使用某个大礼包（前提是不超过需求量）-> 递归求解剩余需求
3. **状态转移**：`min_cost(needs) = min(原价总计, min(offer_price + min_cost(needs - offer)))`
4. **记忆化**：needs 向量做 key，用 map 记忆化
5. **剪枝**：过滤掉价格不优惠的大礼包（offer 价格 >= 各项单独购买价格之和）
6. **约束**：n <= 6, needs[i] <= 10，状态空间最多 11^6 约 177 万

## 解法概览

| 解法 | 时间复杂度 | 空间复杂度 | 推荐度 |
|------|-----------|-----------|--------|
| 记忆化搜索 (map) | O(S * K * n) | O(S * n) | ⭐⭐⭐⭐⭐ |
| 记忆化搜索 (编码状态) | O(S * K * n) | O(S) | ⭐⭐⭐⭐ |
| 纯回溯（无记忆化） | 指数级 | O(n) | ⭐⭐ |

其中 S = 状态总数 (最多 11^6), K = 大礼包数量, n = 物品种类数

## 关键提示

1. **状态编码**：needs 向量可直接用 `vector<int>` 做 map 的 key；或将每个需求量用固定位数编码成一个整数
2. **大礼包预过滤**：如果一个大礼包的价格 >= 其中各物品单独购买的总价，则该礼包没有意义，可跳过
3. **不能超买**：使用大礼包后任何物品的需求量不能变为负数
4. **大礼包可重复使用**：同一个大礼包可以使用多次
5. **基线计算**：对于任何状态，不用任何礼包直接按原价买是一个上界

## 解法详解

### 解法一：记忆化搜索 + map（推荐）

**思路**：

1. **预处理**：过滤掉不划算的大礼包
2. **DFS(needs)**：
   - 计算不用礼包的原价花费作为初始答案
   - 遍历每个大礼包，检查是否可以使用（不超过 needs）
   - 若可以，递归 DFS(needs - offer)，更新最小花费
3. **记忆化**：用 `map<vector<int>, int>` 缓存已计算的状态

**关键代码逻辑**：
```
dfs(needs):
    if needs in memo: return memo[needs]
    
    cost = sum(needs[i] * price[i])    // 原价购买
    
    for each offer in special:
        new_needs = needs - offer
        if new_needs 合法 (无负数):
            cost = min(cost, offer_price + dfs(new_needs))
    
    memo[needs] = cost
    return cost
```

**为什么用 map 而不是 unordered_map**：
- `vector<int>` 没有默认的 hash 函数，`map` 使用 `operator<` 即可
- 也可以自定义 hash 或将状态编码为整数使用 `unordered_map`

### 解法二：状态编码 + 记忆化

**思路**：将 needs 向量编码为一个整数，每个物品需求量占 4 位（足够表示 0-10）。

- 编码：`code = needs[0] + needs[1]*11 + needs[2]*121 + ...`
- 好处：可以使用 `unordered_map<int, int>`，查找更快
- 解码：通过取模和整除还原各维度

**适用条件**：n <= 6, needs[i] <= 10，编码后最大值约 11^6 约 177 万，int 足够

### 解法三：纯回溯（不推荐）

**思路**：不做记忆化，每次都重新计算。

**问题**：大量重复子问题，时间复杂度指数级。但对于小规模输入（n 小、needs 小）也能通过。

## 易错点

1. **忘记过滤不划算的礼包**：虽然不过滤也能得到正确答案，但会增加不必要的搜索分支，影响性能
2. **超买检查遗漏**：使用礼包后每个物品都需要检查是否超出需求，不仅仅是看总量
3. **map 的 key 类型**：`unordered_map` 不支持 `vector<int>` 作为 key，需要用 `map` 或自定义 hash
4. **基线遗漏**：必须先算原价购买的花费作为初始值，不能只考虑用礼包的方案
5. **大礼包可以重复用**：递归时不需要跳过当前礼包，下一层还可以继续使用同一个礼包
6. **空需求**：当 needs 全为 0 时应返回 0

## 面试追问

**Q1: 为什么不能用贪心（每次选单位折扣最大的礼包）？**

贪心不能保证全局最优。例如：
- price = [1, 1], needs = [2, 2]
- 礼包 A: [2, 0, 1]（2个物品A 只要1元，折扣很大）
- 礼包 B: [1, 1, 1]（1A+1B 只要1元）

贪心可能先用礼包 A（单位折扣大），但最优解是用 2 次礼包 B（总花费 2 元 vs 礼包 A + 2 个 B 单买 = 1 + 2 = 3 元）。

不同礼包之间存在"互斥"关系（用了一个可能导致另一个无法使用），必须搜索所有组合。

**Q2: 如果物品种类 n 很大（比如 20），这个方法还可行吗？**

n = 20 时，状态空间可达 11^20 约 6.7 * 10^20，完全不可行。此时需要：
- **整数线性规划 (ILP)**：将问题建模为 ILP，使用专业求解器
- **分支定界**：利用线性松弛的下界进行剪枝
- **近似算法**：如果允许近似解，可以用贪心或启发式搜索

本题限制 n <= 6 正是为了保证记忆化搜索的可行性。

**Q3: 如何优化常数因子？**

- **状态编码为整数**：避免 map 对 vector 比较的开销
- **预过滤礼包**：去掉不划算的礼包减少分支
- **排序礼包**：按折扣力度从大到小排序，可能更早找到最优解（配合剪枝）
- **位运算编码**：如果 needs[i] <= 15，每个维度用 4 位，6 维只需 24 位，一个 int 搞定

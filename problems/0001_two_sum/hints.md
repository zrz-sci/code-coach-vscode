# 1. 两数之和

## 核心思路

本质上就是一个**查找配对**的问题：对于数组中的每个元素 `nums[i]`，能否快速找到另一个元素等于 `target - nums[i]`？

## 思维链

1. **读完题第一反应** → 最直接的做法：对每个数，遍历剩下的数，看有没有配对的。两层 for 循环搞定。
2. **暴力解的瓶颈在哪？** → 外层循环固定一个数后，内层循环做的事情就是"在剩余元素中查找一个特定值"，这个查找操作是 O(n)，总体就是 O(n²)。
3. **怎么突破瓶颈？** → 查找操作从 O(n) 降到 O(1)？哈希表（`unordered_map`）天生干这个事。
4. **具体怎么用？** → 遍历数组时，对每个 `nums[i]`，先查哈希表里有没有 `target - nums[i]`。如果有，直接返回两个索引；如果没有，把 `nums[i] → i` 存进哈希表，供后面的元素来配对。
5. **为什么"边遍历边建表"就够了？** → 如果 `(i, j)` 是答案且 `i < j`，当遍历到 `j` 时，`nums[i]` 已经在表里了。先查后存的顺序保证不会用同一个元素两次。

## 解法概览

| 解法 | 思路 | 时间 | 空间 | 面试 |
|------|------|------|------|------|
| 暴力双循环 | 枚举所有 (i,j) 对 | O(n²) | O(1) | 能说出即可 |
| 哈希表（一次遍历） | 边查边存，O(1) 查找配对 | O(n) | O(n) | ⭐ 必须写出 |
| 排序 + 双指针 | 排序后左右指针夹逼 | O(n log n) | O(n) | 加分项（需要讨论局限性） |

## 关键提示

1. **转换问题**：`nums[i] + nums[j] == target` 等价于 `nums[j] == target - nums[i]`，所以问题变成了"查找 `target - nums[i]` 是否存在"。
2. **用什么存？** 我们需要的是"值 → 索引"的映射，所以用 `map`（而不是 `set`），因为最终要返回索引。
3. **先查后存**：遍历到 `nums[i]` 时先查表、再存入，这样自然避免了"自己和自己配对"的问题（比如 `[3,3], target=6`）。
4. **排序解法的陷阱**：排序会打乱原始索引，需要额外保存原始索引。题目要求返回的是**原始下标**，不是排序后的下标。
5. **Follow-up 已回答**：题目问"能否小于 O(n²)？"，哈希表解法 O(n) 就是答案。

## 解法详解

### 解法1: 暴力双循环 — O(n²) / O(1)

**思考过程**: 最直接的想法——既然要找两个数的和等于 target，就把所有可能的两个数的组合都试一遍。

```cpp
class Solution {
public:
    vector<int> twoSum(vector<int>& nums, int target) {
        int n = nums.size();
        for (int i = 0; i < n; i++) {
            for (int j = i + 1; j < n; j++) {
                if (nums[i] + nums[j] == target) {
                    return {i, j};
                }
            }
        }
        return {}; // 题目保证有解，实际不会走到这
    }
};
```

**关键点**:
- 内层从 `j = i + 1` 开始，而不是 `j = 0`，避免重复检查和自身配对。
- 时间 O(n²) 对于 n ≤ 10⁴ 约 10⁸ 次操作，勉强能过但很慢。
- 这个解法的价值：**明确了瓶颈在"查找配对"这个操作上**。

---

### 解法2: 哈希表（一次遍历） — O(n) / O(n) ⭐ 面试首选

**从解法1优化**: 解法1的瓶颈是内层循环——对每个 `nums[i]`，需要 O(n) 遍历去找 `target - nums[i]`。如果我们用哈希表存已经遍历过的元素，查找就只需要 O(1)。

```
示例: nums = [2, 7, 11, 15], target = 9

遍历过程:
i=0: 查找 9-2=7 → 表中无7 → 存入 {2:0}
i=1: 查找 9-7=2 → 表中有2, 索引0 → 返回 [0, 1] ✓
         ↑
     这就是为什么"边查边存"能找到配对:
     遍历到7时, 它的配对2已经在前面被存进表了
```

```cpp
class Solution {
public:
    vector<int> twoSum(vector<int>& nums, int target) {
        unordered_map<int, int> seen; // 值 → 索引
        for (int i = 0; i < nums.size(); i++) {
            int complement = target - nums[i];
            // 先查: 配对元素是否已经在表中
            if (seen.count(complement)) {
                return {seen[complement], i};
            }
            // 后存: 当前元素存入表中, 供后续元素配对
            seen[nums[i]] = i;
        }
        return {};
    }
};
```

**关键点**:
- **先查后存的顺序至关重要**：如果先存后查，`[3,3], target=6` 时 `i=0` 存入 `{3:0}` 后再查 `3`，会找到自己（索引0），而不是配对的另一个3。先查后存时，`i=0` 查表为空，存入 `{3:0}`；`i=1` 查表找到 `{3:0}`，返回 `[0,1]`，正确。
- `unordered_map` 的平均查找/插入是 O(1)，最坏 O(n)（哈希冲突），但实际面试和 OJ 上认为是 O(1)。

---

### 解法3: 排序 + 双指针 — O(n log n) / O(n)

**不同视角**: 如果数组有序，可以用左右双指针从两端向中间夹逼。但原题需要返回**原始索引**，排序会破坏索引，所以需要额外存储。

```
排序后双指针过程:
原始: [3, 2, 4], target = 6
带索引排序: [(2,1), (3,0), (4,2)]

left=0, right=2: 2+4=6 == target → 返回原始索引 [1, 2] ✓

为什么双指针有效 (不会漏解)?
- sum < target: left右移 (让sum变大), 因为right已经是最大了
- sum > target: right左移 (让sum变小), 因为left已经是最小了
- sum == target: 找到
```

```cpp
class Solution {
public:
    vector<int> twoSum(vector<int>& nums, int target) {
        int n = nums.size();
        // 保存 (值, 原始索引) 对
        vector<pair<int, int>> sorted_nums(n);
        for (int i = 0; i < n; i++) {
            sorted_nums[i] = {nums[i], i};
        }
        // 按值排序
        sort(sorted_nums.begin(), sorted_nums.end());
        
        int left = 0, right = n - 1;
        while (left < right) {
            int sum = sorted_nums[left].first + sorted_nums[right].first;
            if (sum == target) {
                return {sorted_nums[left].second, sorted_nums[right].second};
            } else if (sum < target) {
                left++;   // 和太小, 左指针右移让和变大
            } else {
                right--;  // 和太大, 右指针左移让和变小
            }
        }
        return {};
    }
};
```

**关键点**:
- 这个解法比哈希表解法**慢**（O(n log n) vs O(n)），但它的思路在 **3Sum、4Sum** 等问题中更实用（哈希表在多数之和中容易重复计数）。
- **必须保存原始索引**，这是很多人忘记的点。直接对 `nums` 排序后索引就丢了。

## 解法对比

|  | 暴力双循环 | 哈希表 | 排序+双指针 |
|--|-----------|--------|------------|
| 时间 | O(n²) | **O(n)** | O(n log n) |
| 空间 | **O(1)** | O(n) | O(n) |
| 适用场景 | n 很小时 | **通用首选** | 数组本身有序时；或扩展到 3Sum/4Sum |
| 返回索引 | 天然支持 | 天然支持 | 需额外处理 |

**面试选择**: 99% 的情况直接写哈希表解法。排序+双指针在面试官追问"如果数组有序呢？"时讲。

## 易错点

1. **先存后查导致自身配对**：
   - ✗ `seen[nums[i]] = i; if (seen.count(complement))` → `[3,3], target=6` 时 `i=0` 自己匹配自己
   - ✓ `if (seen.count(complement)) ... ; seen[nums[i]] = i;` → 先查后存

2. **内层循环起点写错**：
   - ✗ `for (int j = 0; j < n; j++)` → 会把 `(i, i)` 当成答案
   - ✓ `for (int j = i + 1; j < n; j++)`

3. **排序解法忘记保存原始索引**：
   - ✗ 直接 `sort(nums.begin(), nums.end())` 后返回双指针位置 → 返回的是排序后的索引
   - ✓ 用 `pair<int,int>` 保存 `(值, 原始索引)` 再排序

4. **哈希表用 `[]` 查询不存在的键**：
   - ✗ `if (seen[complement] != ...)` → `[]` 会自动插入默认值，污染哈希表
   - ✓ `if (seen.count(complement))` 或 `if (seen.find(complement) != seen.end())`

## 面试追问

**Q1: 暴力解法能过吗？瓶颈在哪？**
> 能过（n ≤ 10⁴，O(n²) ≈ 10⁸ 勉强），但瓶颈在查找配对是 O(n)。用哈希表查找降到 O(1)。

**Q2: 如果数组已经排好序了呢？**
> 可以用双指针，O(n) 时间 O(1) 空间（不需要额外存索引，因为假设有序就直接用双指针的索引位置）。这比哈希表的 O(n) 空间更优。

**Q3: 如果需要找所有配对（可能有多个答案）呢？**
> 哈希表：用 `unordered_map<int, vector<int>>` 存一个值对应的所有索引。找到配对时，从两个索引列表中组合出所有 `(i, j)` 对。双指针：找到一对后不返回，而是两个指针同时移动继续找，注意跳过重复值。

**Q4: 如果这个函数会被大量调用（相同数组，不同 target），怎么优化？**
> 预处理：排序一次 O(n log n)，之后每次查询用双指针 O(n)。或者建一次哈希表 O(n)，每次查询 O(n)。核心思想是把一次性工作提到预处理阶段。

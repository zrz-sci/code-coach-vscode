# 652. 寻找重复的子树 (Find Duplicate Subtrees)

**难度**: Medium | **标签**: Tree, DFS, Hash Table, Binary Tree

## 核心思路

将每棵子树**序列化**为唯一字符串表示，用哈希表统计每种序列化出现的次数。当某种子树序列化第二次出现时，将该子树根节点加入结果集。本质上是**后序遍历 + 子树指纹**的思路。

进阶优化：为避免字符串拼接带来的 O(n^2) 开销，可以用**三元组 ID 映射**（将 `(node.val, leftId, rightId)` 映射为唯一整数 ID），将序列化从字符串降维到整数，复杂度降至 O(n)。

## 思维链

1. **问题转化**：判断两棵子树是否"相同" -> 需要一种方式唯一标识每棵子树的结构和值
2. **序列化表示**：对每棵子树做后序遍历，将结构序列化为字符串（包含值和左右子树信息）
3. **去重检测**：用哈希表记录每种序列化出现的次数，首次重复时收集结果
4. **优化考量**：字符串拼接开销大 -> 改用整数 ID 映射来标识子树
5. **边界处理**：空节点需要特殊标记（如 "#"），否则不同结构可能产生相同序列化

## 解法概览

| 解法 | 时间复杂度 | 空间复杂度 | 特点 |
|------|-----------|-----------|------|
| 字符串序列化 + 哈希表 | O(n^2) | O(n^2) | 直观易懂，字符串拼接有额外开销 |
| 三元组 ID 映射 | O(n) | O(n) | 最优解，避免字符串拼接 |

## 关键提示

1. **后序遍历是关键**：必须先处理完左右子树，才能构建当前子树的表示
2. **空节点标记不可省**：`serialize(null)` 必须返回一个特殊标记（如 "#"），否则 `[1, null, 2]` 和 `[1, 2, null]` 会被认为相同
3. **分隔符必不可少**：序列化字符串中各部分之间需要分隔符，否则 `(1, 23)` 和 `(12, 3)` 会混淆
4. **恰好第二次出现时加入结果**：用 `count == 2` 判断，避免重复添加
5. **三元组 ID 技巧**：将 `(val, leftId, rightId)` 映射为自增 ID，用 `unordered_map` 存储

## 解法详解

### 解法一：字符串序列化 + 哈希表

**思路**：后序遍历整棵树，对每个节点构建子树的序列化字符串。将序列化作为 key 存入哈希表计数。

**步骤**：
1. 定义递归函数 `serialize(node)`，返回以 `node` 为根的子树序列化字符串
2. 空节点返回 `"#"`
3. 非空节点：`leftStr + "," + rightStr + "," + to_string(node->val)`（后序格式）
4. 将返回的字符串作为 key，在哈希表中计数
5. 当计数恰好为 2 时，将当前 node 加入结果数组

**复杂度分析**：
- 字符串拼接在最坏情况下（链状树），每层字符串长度递增，总拼接代价 O(n^2)
- 空间同理，哈希表存储所有序列化字符串总长 O(n^2)

### 解法二：三元组 ID 映射（最优）

**思路**：避免字符串操作，用整数 ID 唯一标识每棵子树。

**步骤**：
1. 空节点 ID 固定为 0
2. 对每个非空节点，递归获取 leftId 和 rightId
3. 构建三元组 `(node->val, leftId, rightId)`
4. 在 `map<tuple<int,int,int>, int>` 中查找该三元组：
   - 若不存在：分配新 ID（自增计数器）
   - 若已存在：获取已有 ID
5. 用另一个 `unordered_map<int, int>` 统计每个 ID 出现次数
6. 出现次数恰好为 2 时加入结果

**复杂度**：时间 O(n)，空间 O(n)

## 易错点

1. **忘记处理空节点标记**：导致不同结构的子树产生相同序列化。例如 `[0, null, 0]` 和 `[0, 0, null]` 如果不区分空节点方向就会误判
2. **序列化无分隔符**：`"12#3"` 和 `"1#23"` 会混淆，必须用逗号等分隔符
3. **重复添加结果**：使用 `count >= 2` 而非 `count == 2`，导致同一子树被多次添加到结果中
4. **前序 vs 后序选择**：虽然前序也能工作，但后序更自然（先构建子树表示再构建当前节点表示）
5. **三元组 ID 方案中忽略 val 的范围**：val 可以为负数，三元组的 hash 需要能处理负值

## 面试追问

1. **Q: 如果节点值范围很大（比如 64 位整数），字符串序列化会有什么问题？**
   - A: 字符串更长，拼接开销更大。此时三元组 ID 方案优势更明显，因为 ID 始终是小整数。

2. **Q: 如何用 O(n) 时间解决此问题？**
   - A: 使用三元组 (val, leftId, rightId) -> ID 的映射，避免所有字符串操作。每个节点只做常数时间的 map 查找和插入。

3. **Q: 如果树非常大（百万节点），如何优化内存？**
   - A: 三元组 ID 方案已经是 O(n) 空间。如果还需优化，可以考虑流式处理或分治，但一般场景 O(n) 已经足够。

4. **Q: 这道题与 "判断子树" (LeetCode 572) 的区别？**
   - A: 572 只需判断某棵树是否是另一棵树的子树（一对一比较），而 652 需要找出所有重复的子树（全局去重）。572 可以暴力 O(n*m)，652 的序列化方案更高效。

5. **Q: 能否用树的哈希（tree hashing）来解决？如何处理哈希冲突？**
   - A: 可以。给每棵子树计算哈希值。但哈希冲突是风险：如果两棵不同子树哈希相同会产生误报。可以用多重哈希或在哈希相同时做精确比较来规避。

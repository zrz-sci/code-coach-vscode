# 1488. 避免洪水泛滥

## 核心思路

本质上是一个**贪心调度问题**：晴天是有限的"资源"，你需要把每个晴天分配给某个湖泊去抽干，关键在于——当一个湖泊即将第二次下雨时，你必须在两次下雨之间找到一个晴天去抽干它，而且应该找**最近的那个晴天**（贪心，把更晚的晴天留给后面的需求）。

## 思维链

1. **读完题第一反应**：每天要么下雨（不可控），要么晴天（你选择抽干哪个湖）。洪水 = 某个满的湖又下雨了。所以问题是：如何安排晴天的抽干操作，使得没有湖在满的时候再次下雨。

2. **什么时候会出问题？** 只有当湖泊 `x` 已经满了，又要对 `x` 下雨时才会洪水。所以我们需要在两次对 `x` 下雨的间隔中，找到一个晴天来抽干 `x`。

3. **暴力思路**：当遇到湖泊 `x` 第二次下雨时，回头扫描两次下雨之间有没有可用的晴天。瓶颈：每次回头扫描是 O(n)，总体最坏 O(n²)。

4. **优化瓶颈**：回头找晴天太慢。能不能把所有晴天的索引存起来，当需要时快速找到"两次下雨之间最早的那个晴天"？这就是在一个有序集合中**查找第一个 ≥ 某值的元素**——经典的 **`lower_bound` / 二分查找**！

5. **贪心策略**：用 `set<int>` 存所有未使用的晴天索引。当湖 `x` 第二次下雨时，在 set 中找第一个 ≥ 上次下雨日的晴天索引。为什么找最早的？因为越晚的晴天越有可能给后面的湖泊用（贪心：用最紧迫的资源）。

6. **数据结构选择**：`unordered_map<int,int>` 记录每个湖上次下雨的日期，`set<int>` 维护可用晴天（有序，支持 `lower_bound`）。

## 解法概览

| 解法 | 思路 | 时间 | 空间 | 面试 |
|------|------|------|------|------|
| 暴力回扫 | 每次洪水风险时线性扫描找晴天 | O(n²) | O(n) | 能说出即可 |
| 贪心 + 有序集合 | set 存晴天 + lower_bound 查找 | O(n log n) | O(n) | ⭐ 必须写出 |

## 关键提示

1. **什么时候需要抽干？** 不是遇到晴天就立刻决定抽谁——而是"推迟决策"，等到某个湖要第二次下雨时，再回头去占用一个晴天。

2. **为什么要找"最近的"晴天？** 考虑 `rains = [1, 0, 0, 1]`，第 0 天湖 1 满了，第 3 天湖 1 又要下雨，晴天有 day1 和 day2。应该用 day1（最早的），把 day2 留给后面可能的需求。

3. **晴天 ans[i] 填什么？** 如果晴天暂时没被分配，填 `1`（题目说抽空湖无事发生，所以填任意正数即可）。后续如果这个晴天被分配了，再改写。

4. **无解条件**：湖 x 两次下雨之间找不到任何可用晴天 → 返回空数组。

5. **模拟过程**（以 `rains = [1,2,0,0,2,1]` 为例）：
```
Day0: rain(1) → 湖1满, lastRain={1:0}
Day1: rain(2) → 湖2满, lastRain={1:0, 2:1}
Day2: sunny   → 加入可用晴天 set={2}
Day3: sunny   → 加入可用晴天 set={2, 3}
Day4: rain(2) → 湖2已满! 上次day1, 在set中找≥1的 → day2
              → ans[2]=2, set={3}, lastRain={1:0, 2:4}
Day5: rain(1) → 湖1已满! 上次day0, 在set中找≥0的 → day3
              → ans[3]=1, set={}, lastRain={1:5, 2:4}
结果: [-1,-1,2,1,-1,-1] ✓
```

## 解法详解

### 解法1: 暴力回扫 — O(n²) / O(n)

**思考过程**：最直觉的做法。维护每个湖上次下雨的时间，以及每个晴天是否已被使用。当湖 x 即将洪水时，从上次下雨到当前日之间线性扫描找一个可用晴天。

```cpp
class Solution {
public:
    vector<int> avoidFlood(vector<int>& rains) {
        int n = rains.size();
        vector<int> ans(n, 1); // 默认晴天抽干湖1（无事发生）
        unordered_map<int, int> lastRain; // 湖 → 上次下雨的日期
        vector<bool> used(n, false);      // 该晴天是否已被使用
        
        for (int i = 0; i < n; i++) {
            if (rains[i] > 0) {
                ans[i] = -1;
                int lake = rains[i];
                if (lastRain.count(lake)) {
                    // 湖已满，需要在 (lastRain[lake], i) 之间找晴天
                    bool found = false;
                    for (int j = lastRain[lake] + 1; j < i; j++) {
                        if (rains[j] == 0 && !used[j]) {
                            ans[j] = lake;
                            used[j] = true;
                            found = true;
                            break;
                        }
                    }
                    if (!found) return {}; // 无解
                }
                lastRain[lake] = i;
            }
        }
        return ans;
    }
};
```

**关键点**：内层 for 循环在最坏情况下扫描 O(n)，导致整体 O(n²)。比如 `[1, 0, 0, ..., 0, 1]` 这种结构。

### 解法2: 贪心 + 有序集合 (set + lower_bound) — O(n log n) / O(n) ⭐ 面试首选

**从解法1优化**：解法1的瓶颈是"在区间内线性查找可用晴天"。用 `set<int>` 维护所有可用晴天的索引，`lower_bound` 在 O(log n) 内找到第一个 ≥ 目标的晴天。

```cpp
class Solution {
public:
    vector<int> avoidFlood(vector<int>& rains) {
        int n = rains.size();
        vector<int> ans(n, 1);            // 晴天默认填1
        unordered_map<int, int> lastRain; // 湖编号 → 上次下雨日期
        set<int> sunny;                   // 可用晴天的索引（有序）
        
        for (int i = 0; i < n; i++) {
            if (rains[i] == 0) {
                sunny.insert(i); // 先存起来，等需要时再分配
            } else {
                ans[i] = -1;
                int lake = rains[i];
                if (lastRain.count(lake)) {
                    // 湖已满，必须在上次下雨之后找一个晴天抽干
                    auto it = sunny.lower_bound(lastRain[lake] + 1);
                    if (it == sunny.end() || *it >= i) {
                        // 找不到合法晴天，或晴天在当前日之后（不合法）
                        return {};
                    }
                    ans[*it] = lake; // 把那个晴天分配给抽干这个湖
                    sunny.erase(it); // 该晴天已被使用
                }
                lastRain[lake] = i; // 更新上次下雨日期
            }
        }
        return ans;
    }
};
```

**为什么 `lower_bound` 找最早的晴天是正确的贪心？**
- 在两次下雨之间可能有多个晴天。选最早的那个，把更晚的晴天留给后面可能出现的其他湖泊需求。
- 如果选了一个较晚的晴天，可能导致某个更紧迫的需求抢不到晴天。

**关键点**：`*it >= i` 这个判断——晴天必须严格在当前下雨日之前才有用。实际上由于我们只在 `rains[i]==0` 时才 insert，而此时 `i` 还没到，所以 set 中的元素都 `< i`。但为了安全起见（以及清晰表达语义），加上这个检查更好。

> 注意：实际上 `*it >= i` 这个条件在正确实现中不会触发，因为 set 中只有已经遍历过的晴天（索引 < i）。但 `it == sunny.end()` 的检查是必须的。

## 解法对比

| | 暴力回扫 | 贪心 + set |
|---|---|---|
| 时间 | O(n²) | O(n log n) |
| 空间 | O(n) | O(n) |
| 核心操作 | 线性扫描找晴天 | `lower_bound` 二分查找 |
| 面试 | 说明理解题意 | 必须写出 |
| 优势 | 简单直接 | 高效，支持 10⁵ 规模 |

关键区别：将"找可用晴天"从 O(n) 线性扫描优化为 O(log n) 的 `lower_bound`。

## 易错点

1. **✗ 晴天默认填 0 或不填**：
   ```cpp
   vector<int> ans(n, 0); // 错！晴天必须填正数
   ```
   **✓ 晴天默认填 1**：
   ```cpp
   vector<int> ans(n, 1); // 题目要求 ans[i] 是你选择抽干的湖泊编号，填1表示抽空湖（无事发生）
   ```

2. **✗ 晴天立刻决定抽谁**：有些人想在遇到晴天时就决定抽哪个湖，这是错误的！因为你不知道未来哪个湖需要被抽。正确做法是**推迟决策**——先存起来，等需要时再分配。

3. **✗ `lower_bound` 传错参数**：
   ```cpp
   auto it = sunny.lower_bound(lastRain[lake]); // 错！应该是 lastRain[lake]+1
   ```
   上次下雨那天本身不是晴天，所以要找严格 > `lastRain[lake]` 的晴天，即 `lower_bound(lastRain[lake] + 1)`。

4. **✗ 忘记更新 `lastRain[lake]`**：即使湖泊被抽干后再次下雨，也要更新 `lastRain` 为当前日期，否则下次查找区间会错。

5. **✗ 没有 `erase` 已使用的晴天**：用过的晴天必须从 set 中删除，否则会被重复分配。

## 面试追问

**Q1: 为什么不能在遇到晴天时就贪心地抽最"危险"的湖？**
> 因为你不知道未来的信息。比如你觉得湖A危险就抽了A，结果后面湖B也需要抽但没有晴天了。正确的贪心方向是反过来——遇到危机（湖第二次下雨）时，才去分配晴天资源。

**Q2: 能否用优先队列（堆）代替 set？**
> 不太合适。堆只能取最小/最大值，但我们需要的是"第一个 ≥ 某个值的元素"，这是 `lower_bound` 的语义。堆无法支持这种条件查询。用 set（底层红黑树）正好。

**Q3: 如果题目改成"每个晴天可以抽干 k 个湖"，怎么改？**
> 每个晴天插入 k 次索引到 multiset 中（或者用计数方式），其余逻辑不变。每次需要抽干时消耗一个。

**Q4: 如果湖泊数量极大（10⁹），空间上有什么注意的？**
> 我们用的是 `unordered_map`，只记录出现过的湖泊，不会开 10⁹ 大小的数组。这已经是空间高效的了。

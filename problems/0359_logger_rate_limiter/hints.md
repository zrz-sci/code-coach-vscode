# 359. 日志速率限制器

## 核心思路
本质上是一个**"去重 + 冷却时间"**问题：对每条消息，记住它上次被打印的时间，只有当前时间距离上次打印 ≥ 10 秒时才允许再次打印。

## 思维链

1. **读完题第一反应**：每条消息有个"冷却时间"，10 秒内相同消息不能重复打印。我需要记住每条消息上次打印的时间。
2. **怎么记？** 最自然的想法——用一个数据结构存 `message → 上次打印时间` 的映射关系。
3. **用什么数据结构？** 需要按 message 快速查找，哈希表 `unordered_map<string, int>` 正好是 O(1) 查找和更新。
4. **判断逻辑**：查表——如果 message 不在表中，或者 `当前时间 - 上次时间 >= 10`，就打印并更新时间；否则拒绝。
5. **进阶思考**：如果消息种类无限多，哈希表会无限增长。能否清理过期条目？→ 用队列 + 集合维护一个滑动窗口，只保留最近 10 秒的消息。

## 解法概览

| 解法 | 思路 | 时间 | 空间 | 面试 |
|------|------|------|------|------|
| 哈希表记录时间戳 | map 存 message→lastTime | O(1) 每次调用 | O(n) n=不同消息数 | ⭐ 必须写出 |
| 队列+集合(滑动窗口) | 只保留近10秒消息，清理过期 | O(1) 均摊 | O(m) m=10秒内消息数 | 加分项 |

## 关键提示

1. **映射关系**：你需要的核心操作是"根据消息内容查询上次打印时间"——这天然是一个 key→value 的映射。
2. **判断条件**：不是 `> 10`，而是 `>= 10`。仔细看题目：时间戳 t 打印后，t+10 时刻**可以**再次打印。
3. **时间戳是非递减的**：这个条件意味着你不需要处理"时间倒退"的情况，简化了很多逻辑。
4. **空间优化方向**：如果消息种类极多但活跃窗口很小，可以考虑定期清理过期条目。

```
时间线示意:
  t=1: "foo" → 打印 ✓ (首次出现)
  t=2: "bar" → 打印 ✓ (首次出现)
  t=3: "foo" → 拒绝 ✗ (3 < 1+10=11)
  t=8: "bar" → 拒绝 ✗ (8 < 2+10=12)
  t=10:"foo" → 拒绝 ✗ (10 < 11)
  t=11:"foo" → 打印 ✓ (11 >= 11) → 更新为 11
       ↑
       恰好等于 t+10，可以打印！
```

## 解法详解

### 解法1: 哈希表记录时间戳 — O(1) / O(n) ⭐ 面试首选

**思考过程**：我需要快速查询某条消息上次什么时候打印的。"根据字符串快速查值"→ 哈希表。每次调用时查表判断，通过就更新时间。

```cpp
class Logger {
    unordered_map<string, int> msgMap; // message → 下次允许打印的最早时间
public:
    Logger() {}
    
    bool shouldPrintMessage(int timestamp, string message) {
        // 如果消息不在表中，或当前时间已达到允许时间
        if (msgMap.find(message) == msgMap.end() || timestamp >= msgMap[message]) {
            msgMap[message] = timestamp + 10; // 更新：下次最早可在 t+10 打印
            return true;
        }
        return false;
    }
};
```

**关键点**：
- 存"下次允许打印的最早时间" (`timestamp + 10`) 比存"上次打印时间"更直观，判断时直接 `>=` 比较即可。
- 两种存法等价：存 lastTime 则判断 `timestamp - lastTime >= 10`；存 nextAllowed 则判断 `timestamp >= nextAllowed`。

### 解法2: 队列 + 集合（滑动窗口）— O(1) 均摊 / O(m)

**从解法1优化**：解法1的问题是哈希表会**无限增长**——即使某条消息已经过期很久了，它的记录仍然占着内存。如果消息种类达到百万级别，这是个问题。

**核心思路**：只保留最近 10 秒窗口内的消息。用一个队列按时间顺序存储 `(timestamp, message)`，用一个集合存储当前窗口内的消息。每次新消息来时，先把队列中时间戳 ≤ `timestamp - 10` 的过期条目清理掉。

```cpp
class Logger {
    queue<pair<int, string>> q;  // 按时间顺序的消息队列
    set<string> msgSet;          // 当前10秒窗口内的消息集合
public:
    Logger() {}
    
    bool shouldPrintMessage(int timestamp, string message) {
        // 清理过期消息：队头时间 <= timestamp - 10 的都过期了
        while (!q.empty() && q.front().first <= timestamp - 10) {
            msgSet.erase(q.front().second);
            q.pop();
        }
        // 判断当前消息是否在窗口内
        if (msgSet.count(message)) {
            return false; // 10秒内已打印过
        }
        q.push({timestamp, message});
        msgSet.insert(message);
        return true;
    }
};
```

**关键点**：
- 清理条件是 `<= timestamp - 10`（即严格过期了的才移除）。在 t=11 时，t=1 的消息 `1 <= 11-10=1` 过期被移除，所以 "foo" 可以再次打印。
- 均摊 O(1)：每个消息最多入队一次、出队一次。
- 空间从 O(所有不同消息) 降到 O(10秒窗口内的消息数)。

## 解法对比

| | 解法1: 哈希表 | 解法2: 队列+集合 |
|---|---|---|
| 实现复杂度 | 极简，5行核心代码 | 中等，需要维护两个数据结构 |
| 时间 | O(1) | O(1) 均摊 |
| 空间 | O(所有不同消息) 永不释放 | O(10秒内消息) 自动清理 |
| 适用场景 | 消息种类有限 | 消息种类极多，需要控制内存 |
| 面试推荐 | ⭐ 先写这个 | 作为 follow-up 补充 |

## 易错点

1. **边界条件 `>=` vs `>`**：
   - ✗ `if (timestamp > msgMap[message])` — 漏掉了恰好等于的情况
   - ✓ `if (timestamp >= msgMap[message])` — t+10 时刻可以打印
   - 题目说"直到时间戳变为 t+10 **之前**不打印"，即 t+10 时刻可以打印

2. **首次消息的处理**：
   - ✗ 先判断 `timestamp >= msgMap[message]`，没检查 key 是否存在 → `msgMap[message]` 会插入默认值 0
   - 其实这个"bug"恰好能 work（默认值 0，任何 timestamp >= 0 都成立），但依赖默认值是不好的习惯
   - ✓ 先检查 `find() == end()` 或用 `count()`

3. **解法2清理条件写错**：
   - ✗ `q.front().first < timestamp - 10` — t=1 的消息在 t=11 时不会被清理（1 < 1 为 false）
   - ✓ `q.front().first <= timestamp - 10` — t=1 的消息在 t=11 时正确清理

## 面试追问

**Q1（基础理解）**：为什么用哈希表而不是数组？
> 消息是字符串，不能直接做索引。哈希表支持 O(1) 的字符串查找。

**Q2（空间优化）**：如果消息种类有数百万，但同一时刻活跃的很少，怎么优化内存？
> 用解法2的队列+集合方案，只保留 10 秒滑动窗口内的消息，过期自动清理。空间从 O(全部消息种类) 降到 O(窗口内消息数)。

**Q3（并发变体）**：如果多线程同时调用 `shouldPrintMessage`，怎么保证正确性？
> 需要加锁（mutex）保护 map 的读写操作。或者用 `ConcurrentHashMap`（Java）/ 读写锁来提高并发度。核心是"查询+更新"必须是原子操作。

**Q4（设计变体）**：如果时间戳不是单调递增的（乱序到达），解法2还能用吗？
> 不能直接用队列了（队列依赖时间有序）。解法1 仍然可以，但需要改判断逻辑：只有新时间戳更大时才更新。`if (timestamp >= map[msg]) { map[msg] = timestamp + 10; return true; }`
